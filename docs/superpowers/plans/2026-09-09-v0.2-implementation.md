# IDS-Composit v0.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Freeze v0.1 at tag `v0.1.0`, then add the first v0.2 vertical slice for chapterized specifications, a provenance-aware Known Character Index, data-driven spatial IDC coverage, resolver chaining, and calibration evidence without changing the v0.1 runtime contract.

**Architecture:** Keep the existing Runtime / Render API as the thin integration boundary. Add independent `known`, structural data, and calibration modules; the resolver orchestrates provider order but each provider returns only character knowledge. Calibration tools consume Known Index and structural data but are never imported by the production renderer.

**Tech Stack:** TypeScript, Vite, Vitest, jsdom, GitHub Pages, Node.js standard library only for initial calibration utilities.

**Spec:** `docs/v0.2/00_INDEX.md` and `docs/v0.2/source/01_IDS-Composit_v0.2_要件・アーキテクチャ仕様書.md`

## Global Constraints

- v0.1 public API, fallback behavior, DOM integration, observer behavior, contenteditable policy, copy behavior, and accessibility remain compatible.
- Runtime output remains DOM/CSS; Canvas/SVG are allowed only under `tools/calibration/`.
- Known Character Index is a provenance-aware complement to CHISE, not an ontology, registry, or CHISE replacement database.
- Spatial IDC definitions are data-driven; reflection and rotation remain outside v0.2.0.
- Known Character ambiguity never silently selects an arbitrary character.
- Generic profiles are derived from calibration evidence; per-character calibration is not a runtime character-layout database.
- Every completed task includes focused tests, the relevant docs update, and a fresh regression gate.
